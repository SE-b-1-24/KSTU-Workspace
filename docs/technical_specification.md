**Полное наименование разрабатываемой системы:**
«Корпоративная система мониторинга, управления проектной деятельностью и графовой базой знаний с интеллектуальным ассистентом».

**Краткое наименование:**
«KSTU Workspace».

---

## 1. Назначение разработки

Разрабатываемая система предназначена для организации единого изолированного цифрового пространства предприятий, команд и индивидуальных лиц с целью устранения фрагментации контекста между различными сервисами для организации рабочих процессов. Ядро системы предметно-нейтрально. Специфичные функции реализуются как подключаемые модули.

Система объединяет функции управления задачами, организации файловой системы, ведения документации и контекстного интеллектуального поиска на основе локальной базы знаний с применением технологий Retrieval-Augmented Generation (RAG).

---

## 2. Требования к системе в целом

Система должна функционировать как веб-приложение с модульной архитектурой и обеспечивать взаимодействие клиентской и серверной частей. Развёртывание — On-Premise в локальной сети, без обязательной зависимости от облачных провайдеров, с возможностью подключения внешних LLM.

---

## 3. Требования к функциям системы

Функциональность делится на ядро (обязательно для всех пространств) и опциональные модули, включаемые владельцем пространства:

**Core:**
Управление задачами, база знаний, файловое хранилище, ИИ-ассистент.

**Опциональные модули:**
Интеграция с Git, диаграмма Ганта, OCR-распознавание.

Отключённый модуль скрывается из интерфейса пространства и не участвует в работе.

Система проектируется с программным интерфейсом модуля, позволяющим добавлять новые модули без изменения ядра. Публичный маркетплейс модулей от сторонних разработчиков в рамки текущей разработки не входит и указан как перспектива развития.

### 3.1. Подсистема управления доступом и рабочими пространствами

- регистрацию и аутентификацию пользователей;
- ролевое разграничение прав внутри рабочих пространств (Владелец, Редактор/Участник, Читатель);
- создание пользовательских ролей с возможностью назначения прав;
- создание, конфигурирование и архивацию изолированных рабочих пространств;
- управление подключёнными плагинами/модулями в рамках пространства.

### 3.2. Подсистема управления задачами

- создание, редактирование и удаление задач различных типов;
- назначение исполнителей, приоритетов, дедлайнов;
- интерактивное отображение задач в виде Канбан-доски с перемещением карточек (Drag-and-Drop);
- настраиваемый жизненный цикл задач (пользовательские статусы этапов);
- опциональное представление временной шкалы проекта (диаграмма Ганта).

### 3.3. Подсистема базы знаний и графа связей

- создание и иерархическое хранение статей документации и регламентов;
- встроенный редактор форматированного текста с поддержкой синтаксиса Markdown;
- создание двунаправленных связей между статьями и задачами синтаксисом `[[Название]]` и `[[#ID_задачи]]`;
- интерактивная 2D-визуализация графа ассоциативных связей проектных артефактов;
- загрузка и связывание файлов (PDF, PNG, DOCX) с контекстом задач и статей.

### 3.4. Подсистема корпоративного файлового хранилища

- иерархическое дерево папок и файлов в рамках рабочего пространства;
- загрузка, просмотр, переименование, перемещение, удаление файлов (PDF, DOCX, XLSX, PPTX, PNG, JPEG) с валидацией MIME-типов;
- привязка файлов к задачам и статьям;
- версионирование файлов при повторной загрузке одноимённого документа;
- фоновая асинхронная обработка DOCX/PDF: извлечение текста → разбиение на чанки → генерация эмбеддингов → сохранение в pgvector;
- для изображений — опциональный OCR-модуль, без него файл индексируется только по метаданным (имя, папка, привязки);
- отображение статуса индексации документа в интерфейсе.

### 3.5. Подсистема автоматизации и версионирования

- приём и валидация входящих вебхуков от систем контроля версий;
- парсинг сообщений коммитов на наличие идентификаторов задач;
- автоматический перевод карточки задачи в соответствующий статус и фиксация ссылки на коммит в журнале задачи.

### 3.6. Подсистема интеллектуального ассистента

- парсинг и разбиение Markdown-документов и описаний задач на текстовые фрагменты (chunks);
- генерация векторных представлений (embeddings) фрагментов через внешние или локальные модели;
- сохранение векторов в PostgreSQL (pgvector);
- поиск контекстов по текстовому запросу пользователя;
- синтез ответа через LLM строго на основе найденного контекста с обязательным формированием списка цитируемых источников (citations).

## 4. Требования к видам обеспечения

**Информационное обеспечение:**
Информационная база включает реляционные схемы пользователей, пространств, задач, связей графа, метаданных документов, векторных представлений (таблица чанков с вектором `vector(1024)`), сессий диалогов и журнала аудита.

**Программное обеспечение:**
- Backend: Python 3.11+, FastAPI, SQLAlchemy, asyncpg, Alembic, Pydantic v2, pytest.
- Frontend: React 18, TypeScript, Vite, Tailwind CSS, компонентные библиотеки графов (Force Graph / Cytoscape) и Markdown-редактора.
- Инфраструктура: Docker Engine, Docker Compose, PostgreSQL 16 с расширением pgvector.

**Лингвистическое обеспечение:**
Интерфейс пользователя и системные сообщения ориентированы на русский и кыргызский языки. База знаний и ИИ-ассистент поддерживают обработку запросов на русском, кыргызском и английском языках.

**Техническое обеспечение:**
Развёртывание системы осуществляется на вычислительных мощностях локальной корпоративной сети организации без жёсткой зависимости от внешних облачных провайдеров.

## 5. Требования к надёжности и безопасности

К системе предъявляются следующие требования:

- пароли пользователей хранятся исключительно в хешированном виде с применением алгоритма bcrypt;
- закрытые ключи, токены и конфигурации подключения к СУБД передаются исключительно через переменные окружения (`.env`), их хранение в репозитории запрещено;
- изоляция контекста: пользователь не имеет доступа к задачам, документам и векторным индексам чужих изолированных рабочих пространств;
- предотвращение инъекций: валидация всех входящих параметров через схемы Pydantic на стороне API;
- безопасное хранение файлов: запрет прямого исполнения скриптов в каталоге загрузок, генерация уникальных UUID-имён для файлов;
- транзакционная целостность: каскадное удаление или архивация связанных сущностей, предотвращение появления неконсистентных векторов при удалении документов;
- отказоустойчивость: корректная обработка сбоев внешних LLM-провайдеров без аварийной остановки бэкенда.

## 6. Требования к программному и аппаратному обеспечению

**Минимальные системные требования:**
- Процессор: 4 ядра (x86_64 / ARM64);
- Оперативная память: от 8 ГБ RAM;
- Дисковое пространство: от 25 ГБ свободного места на SSD;
- Операционная система: Windows 10/11 (с WSL2), macOS или Linux (Ubuntu 22.04+);
- Установленное ПО: Docker Desktop / Docker Engine (compose v2), Python 3.11+, Node.js 20+.

**Рекомендуемая конфигурация (для автономного развёртывания со встроенной локальной LLM через Ollama):**
- Процессор: 8 ядер и более;
- Оперативная память: 16–32 ГБ RAM DDR4 и поколениями выше;
- Дискретная видеокарта (GPU): NVIDIA с объёмом видеопамяти от 8–16 ГБ (CUDA);
- Дисковое пространство: от 100 ГБ NVMe SSD.
